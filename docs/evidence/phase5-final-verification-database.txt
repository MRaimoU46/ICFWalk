# Phase 5 final verification: database

Clean disposable database, migrations 001-005 applied in order, then the complete set reapplied to
the same database to prove idempotence.

Sequence executed:

    docker exec icfwalk-mssql sqlcmd -Q "ALTER DATABASE [icfwalk_dev] SET SINGLE_USER WITH ROLLBACK IMMEDIATE;
                                         DROP DATABASE [icfwalk_dev]; CREATE DATABASE [icfwalk_dev];"
    # confirmed empty: SELECT COUNT(*) FROM sys.schemas WHERE name='icf'  ->  0
    node scripts/db/apply-schema.mjs        # first apply, 001..005 in order   -> exit 0
    node scripts/db/apply-schema.mjs        # reapply the complete set         -> exit 1, see below
    npm run test:db

## How to read the reapply exit code

The reapply exits 1, and that is the designed behavior, not a failure of this candidate.
`001_schema.sql` is a create-only script that refuses to run against a database whose `icf` schema
already contains tables ("The icf schema already contains tables. No changes were made."), exactly
as `docs/LOCAL_SETUP.md` and `database/README.md` specify. `apply-schema.mjs` sets a non-zero exit
when any script in the set reports not-ok, so 001's intentional refusal alone produces exit 1.

The four idempotent migrations each reapply cleanly and each exit 0 on their own:

    node scripts/db/apply-schema.mjs --only 002   -> exit 0
    node scripts/db/apply-schema.mjs --only 003   -> exit 0
    node scripts/db/apply-schema.mjs --only 004   -> exit 0
    node scripts/db/apply-schema.mjs --only 005   -> exit 0

Idempotence was proved directly rather than inferred. A full fingerprint of every object and column
in the `icf` schema was taken after the second application and again after a third application of
002-005, and the two are byte-identical:

    SELECT o.type_desc, s.name, o.name, c.name, TYPE_NAME(c.user_type_id), c.max_length, c.is_nullable
      FROM sys.objects o JOIN sys.schemas s ON s.schema_id = o.schema_id
      LEFT JOIN sys.columns c ON c.object_id = o.object_id
     WHERE s.name = 'icf' ORDER BY 1,2,3,4;          -- 455 rows, 22 tables

    sha256(after 2nd apply) = 15b239a37c2ddcf0f2b30760e765d4bad074a95e9270488afdeac64c5f02ddef
    sha256(after 3rd apply) = 15b239a37c2ddcf0f2b30760e765d4bad074a95e9270488afdeac64c5f02ddef

No schema change was made in this session. No migration was edited.

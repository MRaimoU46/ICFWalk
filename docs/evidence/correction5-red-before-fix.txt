Fifth correction session -- deterministic red-before-fix / green-after-fix evidence
=================================================================================

Defect: WalkService.save() and complete() materialized their response DTO with loadDto()
AFTER the mutation transaction had committed and the walk mutation lock had been released,
so another session could commit in between and the response then described THAT state.

Both runs below are the same five regressions, the same database, the same Lucee runtime,
against the real WalkService and the real WalkRepository. The only difference between them
is src/walks/WalkService.cfc: the RED run is the file as commit fa59b16 left it, restored
verbatim (git stash of the correction, Lucee restarted to recompile); the GREEN run is the
same file with the correction applied and Lucee restarted again.

The interleaving is forced deterministically, never by sleeping or racing:
  tests/cfml/support/InterceptingDb.cfc decorates Db.transact and runs a callback at the
  exact instant the mutation transaction commits, before the service method resumes. The
  callback is a real second session committing a real second mutation through the real
  service. tests/cfml/support/InterceptingWalkRepository.cfc fires at countRevisions --
  reached only while the response is being materialized -- and starts a real concurrent
  writer there, joined with a bounded 6000 ms wait.

Reading the failures: the expected value is the rowversion the mutation itself recorded in
icf.walk_mutation; the actual value is two rowversions later -- the state the OTHER session
committed at the boundary. That is the reported defect exactly: the response describes a
state the mutation did not produce, and the client adopts that live token while keeping its
own stale editor state. The fourth failure is the lock itself: the concurrent writer was
observed COMPLETED inside the window, so nothing was holding it back.

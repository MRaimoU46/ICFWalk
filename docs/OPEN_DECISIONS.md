# Open decisions and safe defaults

These items require district or deployment-owner decisions. They must not block the base build, and the implementation must not guess irreversible answers.

| Decision | Safe build default |
| --- | --- |
| Approved wording for 17 placeholder questions | Preserve and visibly flag the current placeholder prompts; make replacement a new DRAFT version edit. **Phase 6:** built that way. The placeholder review queue (`/placeholders`, the Placeholders panel) lists each one with its source location; an administrator resolves one by editing the prompt and review status in a DRAFT, and the queue and `contentReview.unresolvedPlaceholders` shrink. The approved wording itself is still the district's to supply |
| Whether teacher identifier, name, email, and classroom label should appear | Keep nullable, hidden, and excluded from aggregate reports |
| Production SSO provider and claims | Implement an adapter and environment mapping; use a development stub only outside production |
| Hosting topology, datasource name, base URL, and secret store | Use environment/config placeholders and deployment documentation; commit no secrets |
| Aggregate privacy-suppression threshold | Implement a configurable policy seam with no invented threshold; never expose individual rows to report-only roles. **Phase 7:** `ICFWALK_REPORT_SUPPRESSION_THRESHOLD` is empty/0 (none) by default and refuses startup unless it is a whole number. When set to N, a report population below N is withheld whole and each org-unit or dimension-value group below N is withheld individually. Cell-level, complementary and differencing protection are **not** implemented and need this decision first (`docs/DATA_CONTRACT.md`, "How Phase 7 reports implement this") |
| Which walks a report counts | **COMPLETED** walks by default; DRAFT walks only when the person asks (`includeDrafts=true`, labelled "Include walks still in draft"); VOIDED walks never. A district that wants drafts in its standard reports changes the default, not the data |
| Whether a report may pool instrument versions | **No.** A report covers one pinned version (the current one unless another is chosen). Walks under different versions may have different wording or scoring for the same reporting key, so cross-version trend reporting needs an approved mapping of which items are comparable before it is built |
| How the instrument's yearly update is made | **In Excel, first.** The instrument changes once a year, in summer. A version downloads as a workbook, is edited in Excel (structure included), and uploads as a new DRAFT through the normal import; it is previewed, compared and published in the app. A friendlier in-app structural editor is scoped after the first summer cycle, from what actually changed; rules and dimensions stay in Excel unless they turn out to change often. Plan and status: the Phase 6 review document |
| Whether an upload may replace an existing DRAFT without naming it | **No (audit correction P6A-02).** An administrator's upload is create-only; replacing a DRAFT requires naming its id and the checksum the administrator agreed to replace, and the server compares both under the version lock (409 `DRAFT_REPLACEMENT_REQUIRED` / `DRAFT_CHANGED` otherwise). The page still asks before replacing, but the question is how a person chooses, not the protection. The operator's maintenance import keeps re-importing a DRAFT by label, deliberately: it is the seed path, behind the maintenance token, and not reachable by a signed-in user |
| How large a request body may be | **5,000,000 bytes for an instrument import; 20,000,000 bytes for anything else** (audit correction P6A-01), enforced by the router before the body is parsed and after the caller is authenticated. 20,000,000 matches Adobe ColdFusion's default "Maximum size of post data" (20 MB) and is far above any real walk save; the deployment's connector should carry the same ceiling (docs/LOCAL_SETUP.md). A deployment that needs larger bodies changes the router constant and the connector together |
| Where a workbook is parsed | **In the browser.** The server receives the same JSON document any upload sends, so there is no spreadsheet parser, no new upload path and no new attack surface on the server. The cost is that a workbook is only as trustworthy as any other document, which is exactly as trustworthy as import already requires |
| What an administrator may edit in the browser | **Wording only** (section titles, instructions and review status; item prompts, help text, placeholder text, review status and revision notes; option labels and definitions; version review status and notes). Structure -- keys, types, response sets, options, rules, dimensions, order, `behavior`, item `settings` -- is authored in the instrument document and imported. Two authoring paths for structure would drift; the document is already the reviewed source of truth |
| How a retirement is attributed | In the `INSTRUMENT_VERSION_RETIRED` audit event (actor, walk count, successor), with `effective_end` closing the version's service window. No retirement column and no migration. If a deployment needs retirement facts in reporting queries, add a column then |
| Whether the only version in service may be retired | **Only with explicit confirmation**, asked twice in the UI (`allowNoCurrentVersion`). Afterwards no new walk of that instrument can start until another version is published; existing walks and reports are unaffected |
| Whether an administrator may import or publish other instruments | **Yes.** The admin routes accept any instrument code. Only `ICFWALK_INSTRUMENT_CODE` is what walks use, and the version list says which rows those are. Restricting codes would be a deployment policy, not a data rule |
| Whether hidden Period values should be cleared | Retain as HIDDEN by default, exclude from reports/export, and document the policy |
| Whether placeholder warnings block instrument publication | Treat as warnings by default; make blocking policy configurable |
| Migration of browser-local prototype records | Do not attempt automatic migration without an approved export/import process; production begins with SQL as authority |
| Automated outbound teacher email | Disabled. Preserve copy and mailto only until separately authorized |
| Whether an environment that ran the earlier form of migration `006` more than once carries dimension-value memberships it never authored | Detect, never auto-correct. `006` now records its one-time transition and can no longer infer membership, but it deletes nothing it may have inferred before. `database/README.md` carries two read-only detection queries and a reviewed remediation procedure; where a version's frozen snapshot cannot establish the intended membership, the instrument owner must state it in writing before any row is removed |
| Who may change shared instrument metadata (`icf.instrument` name, description, and whether the instrument is in service) | Not the importer, and not merely somebody the database has heard of. `InstrumentMetadataService.updateMetadata` takes the **current principal** and asks `AuthorizationService` for global `instrument.manage` before any mutation; the audit actor is that principal's `userId` and no argument can name another. `DefinitionRepository.userExists` remains, as an **integrity** check for the audit foreign key, and is not authorization. No route is exposed for the operation, and the Phase 6 administration UI does not expose one either: renaming or taking an instrument out of service is a deployment decision nobody has made, and the operation is ready when it is. The absence of a route is a scope decision and is not the security control |
| Whether a shared-metadata patch that produces no material difference is an audited operation or a no-op | **A no-op.** The locked read establishes, under the row lock, that every supplied value already equals the stored one exactly -- `name` and `description` case-sensitively, `active` as a boolean, so a capitalization-only edit is a change; the row is then not written, `updated_at` and `row_version` do not move, and no `INSTRUMENT_METADATA_UPDATED` event is recorded. The result carries `noOp: true` and an empty `changedFields`, so the caller is told plainly. An administrative action that changed nothing is not a change, and an audit trail that records it makes the events that did change something harder to find. A patch naming no supported field at all is a different case and is refused (`INSTRUMENT_METADATA_NO_CHANGES`) |

Fable should complete the application with these defaults and surface each item in configuration or administration documentation.
